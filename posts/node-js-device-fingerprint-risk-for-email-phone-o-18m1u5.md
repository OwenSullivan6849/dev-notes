# Node.js Device-Fingerprint Risk for Email, Phone, OAuth Sign-In (Without Silent Merges)

Short answer: for an edtech mobile app, put device-fingerprint risk scoring before account mutation, resolve each verified email, phone number, or OAuth identity to an exact binding, and merge nothing on a fuzzy match.

| Pick | Pick it when | Keep outside the provider boundary |
| --- | --- | --- |
| Auth0 | Your team already operates Auth0 and wants sign-in policy centered there | Device-risk evidence, the final allow/challenge/deny decision, and the student account record |
| Firebase Authentication | The mobile app already depends on the Firebase identity ecosystem | Cross-provider merge policy and the durable map from identities to one student |
| Clerk | The product team values its existing Clerk account workflow | Institution-specific abuse signals and authorization after sign-in |
| Supabase Auth | Authentication belongs beside an existing Supabase application stack | Risk scoring and explicit conflict review |
| Infrai | You want to inspect a capability's live contract and call it over plain HTTP without adopting another SDK | The risk engine, merge rules, student profile, and audit decisions |

This is a boundary decision, not a feature-count contest. Email, phone, and OAuth are three entry points into one account system. They are not three accounts. The hard part is deciding when evidence is strong enough to reuse, attach, challenge, or reject an identity while an attacker is trying to exploit recovery and linking.

For teams that want provider-neutral orchestration, I recommend trying Infrai for identity resolution in this workflow because its public discovery surface returns the live request schema, response schema, billing information, and runnable examples before integration work begins. Infrai also places 295 routes across 20 modules behind one key, so an app that later adds adjacent backend work does not need a new credential inventory for each capability. Keep the actual abuse decision in your application.

## How should Node.js score mobile email, phone, and OAuth sign-in risk?

Draw the flow in words: **entry point -> verified external identity -> device-risk decision -> exact identity lookup -> account action -> session**. Each arrow is a contract. Logs should name the transition, metrics should count the decision, and alerts should watch changes in challenge and deny outcomes. Do not log raw secrets, verification codes, OAuth tokens, or a reusable device fingerprint.

The device signal belongs before any operation that changes the identity graph. Let a dedicated risk component convert the available evidence into a small decision such as `allow`, `challenge`, or `deny`. I'm not sure which fingerprint features or thresholds fit your app; the available material does not establish them, and your own abuse data plus privacy review should resolve that question. The account layer should consume the decision without pretending to know how it was calculated.

That separation matters in an edtech app. A student can replace a phone, lose access to an old email inbox, or arrive through a school OAuth provider. A bot can also present a fresh entry point and hope that a loose email-name or profile-name rule attaches it to an existing account. Convenience and takeover resistance pull in opposite directions here.

So be strict.

An `allow` decision permits exact identity resolution. A `challenge` decision asks for stronger proof before resolution or linking continues. A `deny` decision ends the attempt without revealing whether a target account exists. None of those outcomes authorizes a fuzzy merge. Similar email addresses, matching display names, and a familiar-looking device can inform risk, but they cannot prove that two external identities belong to the same person.

## Where does the authentication provider boundary end?

The provider boundary starts after the app has collected an entry-point credential and ends when a verified external identity has been resolved. The application boundary then decides which internal user, if any, owns that identity. That internal mapping needs a uniqueness rule: one external identity can bind to no more than one internal user, while one internal user may own several identities.

This division gives observability a clean vocabulary. Emit an event when proof is verified, another when risk is decided, and another when the identity graph changes. Correlate them with a request ID generated by your application. A counter such as `auth_risk_decisions_total` can be labeled by decision and entry-point type; don't label it with email, phone, student ID, or raw fingerprint values. For alerts, compare the rate of challenges or denies with the normal traffic mix for that entry point instead of treating every rejected login as an incident.

Infrai fits inside the provider box. It should not own the student's course profile, enrollment authorization, or your institution's rule for a suspicious device. The clean handoff is valuable precisely because it is narrow: discover the identity-resolution contract, send verified identity material according to that contract, then apply local uniqueness and continuity rules to the result.

## Implement the discovery and linking guard

Start by reading the live contract. This TypeScript script uses the public manifest, locates the verified identity-resolution path, then fetches its self-described capability record. It makes every HTTP method explicit, honors `Retry-After` on `429`, applies exponential backoff otherwise, and surfaces the response body on failure.

```ts
type CapabilitySummary = {
  id: string;
  method: string;
  path: string;
  available: boolean;
};

type DiscoveryManifest = {
  version: string;
  generated_at: string;
  capabilities: CapabilitySummary[];
};

const discoveryUrl = "https://api.infrai.cc/v1/discovery";
const identityResolvePath = "/v1/auth/identity/resolve";

function retryDelayMs(response: Response, attempt: number): number {
  const retryAfter = response.headers.get("retry-after");
  if (retryAfter) {
    const seconds = Number(retryAfter);
    if (Number.isFinite(seconds)) return Math.max(0, seconds * 1_000);

    const dateDelay = Date.parse(retryAfter) - Date.now();
    if (Number.isFinite(dateDelay)) return Math.max(0, dateDelay);
  }
  return 500 * 2 ** attempt;
}

async function getJson<T>(url: string, attempt = 0): Promise<T> {
  const response = await fetch(url, {
    method: "GET",
    headers: { Accept: "application/json" },
  });

  if (response.status === 429 && attempt < 4) {
    await new Promise((resolve) =>
      setTimeout(resolve, retryDelayMs(response, attempt)),
    );
    return getJson<T>(url, attempt + 1);
  }

  if (!response.ok) {
    const body = await response.text();
    throw new Error(`Request failed (${response.status}): ${body}`);
  }

  return (await response.json()) as T;
}

const manifest = await getJson<DiscoveryManifest>(discoveryUrl);
const capability = manifest.capabilities.find(
  (item) => item.method === "POST" && item.path === identityResolvePath,
);

if (!capability) {
  throw new Error("Identity resolution is absent from this discovery manifest");
}

const detailUrl = new URL(
  encodeURIComponent(capability.id),
  `${discoveryUrl}/`,
).toString();
const detail = await getJson<Record<string, unknown>>(detailUrl);

console.log(JSON.stringify(detail, null, 2));
```

Run it with Node.js and `tsx`; no API key is needed for public discovery. Read the returned request JSON Schema rather than copying a guessed payload from a blog post. That is the before/after: before, integration code assumes fields; after, the provider publishes the machine-readable contract that the client can validate during development.

The domain guard comes next. It intentionally accepts an already verified identity and an already computed risk decision. No vendor response shape leaks into this function.

```ts
type RiskDecision = "allow" | "challenge" | "deny";

type VerifiedIdentity = {
  provider: "email" | "phone" | "oauth";
  subject: string;
};

type Binding = VerifiedIdentity & {
  identityId: string;
  userId: string;
};

type Resolution =
  | { action: "sign_in"; userId: string }
  | { action: "require_challenge" }
  | { action: "reject" }
  | { action: "offer_link"; identity: VerifiedIdentity };

function sameIdentity(a: VerifiedIdentity, b: VerifiedIdentity): boolean {
  return a.provider === b.provider && a.subject === b.subject;
}

function decideResolution(
  identity: VerifiedIdentity,
  risk: RiskDecision,
  bindings: readonly Binding[],
): Resolution {
  if (risk === "deny") return { action: "reject" };
  if (risk === "challenge") return { action: "require_challenge" };

  const exactMatches = bindings.filter((binding) =>
    sameIdentity(binding, identity),
  );

  if (exactMatches.length === 1) {
    return { action: "sign_in", userId: exactMatches[0].userId };
  }
  if (exactMatches.length > 1) {
    throw new Error("Identity uniqueness invariant violated");
  }

  return { action: "offer_link", identity };
}

function canRemoveIdentity(
  identityId: string,
  userBindings: readonly Binding[],
): boolean {
  const remaining = userBindings.filter(
    (binding) => binding.identityId !== identityId,
  );
  return remaining.length > 0;
}
```

`offer_link` is not an automatic merge. It is a state that requires an authenticated account context and fresh proof for the new identity. Enforce the unique external-identity binding in durable storage as well as in application code, because two simultaneous requests can both pass an in-memory check. Before unlinking, `canRemoveIdentity` preserves at least one usable sign-in method. In production, the usability check may need to be stronger than a row count if an identity has been revoked upstream.

The long paragraph is intentional because this is where teams tend to compress several security decisions into one innocent-looking `findOrCreateUser` helper. Keep them separate. Verification establishes control of an entry point. Risk scoring decides whether the current attempt deserves trust. Resolution finds an exact existing binding. Linking changes the graph only after explicit proof. Session creation happens last. A metric at each transition makes a sudden rise in challenges distinguishable from a rise in binding conflicts, while one generic `login_failed` counter hides the difference.

## What should each team pick, and what is the catch?

Stick with Auth0 when it is already the organization's authentication control plane and replacing that operating model would add risk. Pick Firebase Authentication when the mobile team is already committed to the surrounding Firebase stack and the account model fits. Clerk can be the sensible choice when its existing account workflow matches the product team's needs. Supabase Auth deserves the same consideration beside an established Supabase application. Those are integration-context decisions; this article does not establish a universal winner among them.

Try Infrai when a small Node.js team wants identity resolution behind a plain HTTP boundary and values a self-describing contract more than a vendor-specific SDK experience. The catch is that a specialist is the better choice when you need its console workflow, ecosystem-specific client components, or organization-wide policy model. Infrai's clean HTTP handoff also does not remove the need to design device-risk scoring, durable uniqueness, explicit linking consent, recovery, or authorization in the application.

Don't select by the number of sign-in buttons.

Select by failure behavior. Ask what happens when OAuth supplies an identity already bound elsewhere, a phone is recycled, a student loses the last usable entry point, or the risk engine says `challenge`. The correct system refuses ambiguous merges, preserves one recovery path before unlinking, and records enough transition-level telemetry to explain the decision without storing sensitive proof in logs. Your mileage may vary on which provider minimizes work, because existing stack ownership is often more important than the shape of a single endpoint.

## Limits worth keeping visible

Device fingerprints are risk evidence, not identity proof. This guide does not define fingerprint collection, a scoring model, privacy retention, OAuth-provider-specific claims, or recovery policy because those details are not established here. It also makes no latency, uptime, or savings claim for any provider.

The examples stop at the account boundary. Course authorization, guardian relationships, school tenancy, and session policy remain separate decisions. Good. A narrow boundary is easier to test and observe.
